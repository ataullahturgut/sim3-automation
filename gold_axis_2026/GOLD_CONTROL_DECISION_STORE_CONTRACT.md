## 0. PURPOSE

The current application expects a file-style latest decision artifact. The project roadmap requires the decision state to become immutable, queryable and auditable in the dynamic Neon data plane.

This contract defines the minimum persistence semantics **without inventing a position/exposure ladder that the recovered R4.1 engine does not currently contain**.

No production database migration is applied by this document.

---

# 1. CRITICAL AUDIT FINDING — CLASSIFICATION IS NOT YET A POSITION ACTION

The current R4.1 `classify_state()` function explicitly describes its output as:

> `Descriptive state only; no unrecovered exposure ladder is invented.`

Its current exact classification vocabulary is:

- `MACRO_DOWN_RISK`
- `REVERSAL_RISK_DOWN`
- `REVERSAL_RISK_UP`
- `ALIGNED_UP`
- `ALIGNED_DOWN`
- `CONFLICT`
- `UNRESOLVED_MIXED`

Therefore the database must store the engine's **descriptive classification** exactly as issued.

It must **not** automatically convert those states into fabricated actions such as `BUY`, `SELL`, `HOLD_LONG`, `REDUCE` or an exposure percentage unless a separate audited execution/position mapping is recovered or frozen under change control.

Current action mapping status:

`NOT_PROVEN_POSITION_MAPPING`

This means the future UI may say what the R4.1 state is and why, but a user-facing position instruction requires its own proven mapping contract.

# 5. LOGICAL ENTITY 1 — `decision_runs`

Purpose: one record for every attempted deterministic decision-engine run.

Minimum conceptual fields:

| Field | Requirement |
|---|---|
| `run_id` | immutable unique ID |
| `decision_as_of` | exact EOD/state timestamp being evaluated |
| `generated_at` | timestamp the engine actually ran |
| `engine_version` | required |
| `config_version` | required |
| `config_hash` | required where available |
| `code_sha` | required for production/shadow evidence |
| `trigger_type` | scheduled/manual/replay/shadow etc. |
| `evidence_class` | `HISTORICAL_REPLAY`, `PROSPECTIVE_SHADOW`, or `LIVE_PRODUCTION` |
| `status` | success/partial/blocked/failure state |
| `input_snapshot_ref` | immutable input/data snapshot reference |
| `forecast_contract_ref` | H=1/monthly contract reference used by the engine |
| `notes` / `metadata` | audit context only |

### Evidence-class rule

`generated_at` and immutable inputs must prove that a state existed before the outcome before it can be labeled `PROSPECTIVE_SHADOW` or `LIVE_PRODUCTION`.

A historical replay executed today remains `HISTORICAL_REPLAY` even if it uses causal code.

# 9. IDEMPOTENCY / UNIQUENESS PRINCIPLE

The same engine/config/code/input snapshot evaluated for the same `decision_as_of` should not create duplicate authoritative snapshots.

Implementation defines a deterministic fingerprint over at least:

- decision as-of
- engine version
- config hash/version
- code SHA
- input snapshot reference
- forecast contract reference.

Repeated persistence of an identical state must be idempotent.

A changed input/revision/code/config is a new lineage, not an overwrite.

The Stage 3 DDL candidate enforces unique fingerprints at run, snapshot and event level.

---

# 10. FAILURE / PARTIAL-RUN POLICY

If a required input is unavailable or fails quality checks:

1. record the run attempt where the store is available;
2. mark run status explicitly;
3. do not fabricate missing signal values;
4. do not create an authoritative `LIVE_PRODUCTION` decision snapshot;
5. surface the latest valid stored decision separately from current pipeline health.

Examples:

- XAU source stale → run may be blocked/partial depending frozen rule;
- monthly contract missing → `BLOCKED_MISSING_MONTHLY_CONTRACT`;
- required EOD close not proven → `BLOCKED_EOD_CLOSE_NOT_PROVEN`;
- macro event absent because full contract is unrecovered → retain nullable/blocked macro state rather than invent consensus history.

Exact failure enum names should be finalized in implementation, but must preserve this no-fabrication behavior.

# 11. APP READ CONTRACT

After Stage 3 is implemented, the app should query:

1. latest **valid stored decision snapshot**;
2. its corresponding event/run provenance;
3. current pipeline health separately.

The app must not:

- recompute a final classification from live spot;
- infer a position action from a descriptive classification;
- treat stale/current market monitoring as an EOD decision;
- overwrite the stored decision because a live price moved afterward.

The visible distinction remains:

`CANLI PİYASA ≠ SON KANONİK EOD KARAR DURUMU`
